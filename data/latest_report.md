### Architecture: Build vs. Buy Decision Framework
**Answer**: "I use a three-axis framework: (1) **Differentiation** — does this create competitive advantage? If yes, build. (2) **Operational maturity** — can we run it better than vendors? Consider team bandwidth, on-call burden, expertise. (3) **Time-to-value** — what's the opportunity cost of building? Real example: At [prior], we evaluated managed Kafka (Confluent) vs. self-hosted Strimzi. Chose Strimzi because we had K8s expertise, needed fine-grained control for multi-tenancy, and the 6-month build investment paid off in 18 months via cost savings and custom quota enforcement. But we bought Auth0 for auth — not differentiating, high compliance burden."

### Distributed Systems: Exactly-Once Semantics
**Answer**: "True exactly-once is impossible in distributed systems — we aim for effectively-once. For event-driven: idempotent consumers with deduplication keys (event ID + processor ID) stored in a transactional outbox table (same DB as business state). Producer writes event + outbox row in single transaction. Relay publishes from outbox with at-least-once; consumer deduplicates. For cross-service sagas: orchestration-based (not choreography) with a state machine persisting step state, compensating transactions for rollback. Key: idempotency keys at every boundary, deterministic processing."

Build self-service interfaces (Backstage, CLI) to reduce ticket queue. Phase 3 (6-12 months): Specialize into sub-teams (infra, DX, SRE) each with a tech lead. Throughout: I stay hands-on on the hardest problems (e.g., K8s upgrade strategy, cost optimization), pair with new hires, and write the first version of critical tools before delegating."
